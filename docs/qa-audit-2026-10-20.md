# FPRS system evaluation - 20 October 2026

## 1. Executive Summary

**Overall health: 60/100. Core inquiry workflows work, but the system should not receive production sign-off until history retention and public-file exposure are corrected.**

This is a severity-weighted engineering assessment using the rubric below. Confidence is strongest for the live local client/director workflows. Admin approval was exercised through isolated fixtures, not an authenticated live admin account.

| Area | Score | Assessment |
|---|---:|---|
| Core functionality | 30/35 | Registration, authentication, inquiry confirmation, questionnaire submission and repeat inquiries worked with dedicated accounts. |
| Data integrity | 10/25 | Package deletion erases recorded experiences; invalid prices/quantities and overlength names can be silently changed. |
| UI/UX and accessibility | 14/25 | Consistent branding and working questionnaire controls, with several reproducible overflow and form-label problems. |
| Access and security | 6/15 | Role/ownership checks work, but repository/research files are publicly reachable and some POST handlers lack CSRF validation. |

### Coverage and evidence

- Environment: local Apache/PHP/MySQL application at `http://127.0.0.1/fprs`, installed Firefox 153.5.0, desktop browser CSS viewports of 320, 375, 768, 1024 and 1536 pixels.
- Three ordinary accounts were registered through the real public form: one client and two directors. No administrator account was created or borrowed.
- Only these audit-owned accounts and their synthetic parlors were approved through a guarded local setup script. This allowed live testing without changing anyone else's approval status. The live administrator approval UI remains a coverage gap.
- **37 live HTTP workflow scenarios: 32 passed, 5 identified problems.** Six additional edge scenarios produced two passes and four findings. Related findings are grouped below rather than treated as independent defects.
- **22 live pages at five widths: 96/110 initial layout checks passed.** After saving a valid 200-character package title, seven affected pages were retested with settled animations: **13/35 targeted stress checks passed**. This targeted sample is reported separately from the initial matrix.
- **28/28 admin fixture layout/modal checks passed** at seven widths. These used the actual templates with isolated fixture records.
- **56 safe internal links checked: no broken destinations.** Destructive GET links, logout and clear-preferences actions were excluded from the crawler.
- Existing backend suite: **59 endpoint scenarios passed**. Questionnaire-source and live-rating JavaScript checks passed. Real MySQL temporary-table checks passed for confirmation, ownership, per-question rollback, fractional averages, duplicate feedback and repeat inquiries.
- For 81 requests in the primary HTTP run, local response times were median **39 ms**, p95 **637 ms**, maximum **852 ms**. These are single-user local HTTP timings, including response-body transfer; external fonts/video/CDN rendering and production load are outside those measurements.

### Primary workflows that passed

Pending accounts could not log in. Approved accounts logged in successfully. Clients could not open director/admin tools; directors could not open admin tools. A revoked client session was redirected to login, and logout prevented reopening the dashboard.

Pending parlor packages stayed hidden from clients. Approved packages appeared in location searches, including searches with a low budget and an unmatched religion preference. Contact-page visits did not create inquiries. An inquiry reached the owning director, while another director could not confirm it. Feedback stayed locked before confirmation, including direct POST attempts. The confirmed form contained 22 questionnaire statements. Partial answers and duplicate feedback were rejected. A saved HTML-like comment was escaped and did not execute. One 5/5 review followed by an independent 2/5 review produced a 3.5/5 package average. After a service was marked availed, a new inquiry required confirmation again. Cancelled inquiries could also be restarted safely.

Registration role toggles, show/hide-password controls, adding a service row, questionnaire selection highlighting and required-answer validation worked in the browser. No broken images were observed in the sampled live pages. Existing admin name/email/action alignment and declined-account modal cancellation passed fixtures.

### Data protection and cleanup

**No fixes were applied to application behavior during this audit.** The repository already contained earlier implementation changes; the audit did not commit, reset or revert them.

Before testing, every existing row in 14 application tables was hashed. After testing and cleanup, **zero pre-existing rows had changed and every audited table's original row count was restored**. This includes the two existing parlor-feedback records, 880 survey-rating entries, and the pre-existing package questionnaire review. Three temporary accounts, their synthetic data and five synthetic uploaded verification images were removed. Cleanup checked account ownership, upload containment and file hashes.

Private evidence, HTTP responses, test scripts, screenshots and integrity manifests are under [the audit artifact directory](../.codex-review/20261020-qa-audit/). Apache denied anonymous access to that directory. Passwords and session cookies are excluded from this report.

### Coverage limits

There were no supplied admin credentials, so live administrator login, approval and deletion journeys are not certified. Cloud Firebase token verification/rules, email delivery, concurrent load, physical phones, Safari/Chrome, assistive-technology operation and a complete accessibility conformance assessment were not performed. There is no implemented checkout/payment journey to test; inquiry confirmation and director-marked availing do not establish payment. The two existing scheduled funeral records have no parlor association on their packages and were left unchanged.

## 2. Critical Functional Bugs

Priority: **P1** = release blocker/high impact; **P2** = significant correctness or security issue; **P3** = refinement/maintenance issue.

### F01 - P1: Deleting a package deletes its inquiry and review history

**Reproduce:** Create an approved test package. Send a client inquiry, confirm it as its director, and submit the questionnaire. Delete that package from the director catalog. Check Inquired Services and the stored feedback.

**Observed:** The inquiry and its submitted review disappear. This was demonstrated with synthetic records only. The chain is `packages -> service_inquiries -> package_feedback -> package_feedback_answers`, using cascading deletion.

**Expected:** Removing a package from the catalog should not silently erase a client's recorded experience and ratings.

**Cause:** [Inquiry foreign key](../sql/20261020_service_feedback.sql) and the hard delete in [package_action.php](../director/package_action.php). Account/parlor deletion helpers also hard-delete packages; retention behavior must be considered when fixing this chain.

### F02 - P1: Repository, schema and research files are served without authentication

**Reproduce:** Make anonymous HTTP HEAD requests to `/.git/HEAD`, `/.git/config`, `/sql/setup.sql`, `/Q_A%20EXCEL.xlsx` and `/Questionnaire4RespondentsNotFinished%20(1).docx` beneath `/fprs`.

**Observed:** All returned HTTP 200. A repository pack-object URL also returned HTTP 200. Workbook contents and repository-object contents were not downloaded for this check.

**Expected:** Deployment metadata, source research workbooks and database setup files should not be public website downloads unless explicitly intended.

**Impact:** Source/deployment information is exposed. The workbook requires owner review to determine whether its contents are appropriate for public distribution; no claim is made here that credentials or personal workbook data were extracted.

**Cause:** Non-public project files reside beneath the document root without covering access rules. The root [.htaccess](../.htaccess) primarily controls error display.

### F03 - P1: Invalid package prices are saved as zero

**Reproduce:** As the test director, POST a new package with valid title/services and `price=not-a-number`.

**Observed:** The package saved successfully with `price=0.00`. Catalogs display that as a peso amount. The form describes zero as custom pricing, which makes silently converting invalid input particularly confusing.

**Expected:** Reject invalid input, preserve the entered data for correction and avoid publishing a different amount.

**Cause:** `max(0, (float)...)` in [package_action.php](../director/package_action.php). The same conversion also changes negative prices into zero.

### F04 - P2: Malformed field types cause HTTP 500

**Reproduce:** POST `email[]=test&password=invalid` to `/login.php`, or request `/client/dashboard.php?search=1&budget[]=5` while signed in as a client.

**Observed:** HTTP 500 instead of a validation response. Normal invalid credentials and malformed messaging JSON were handled correctly, so this is an inconsistent input-validation boundary.

**Expected:** A friendly validation message or 400/422 response, with no state change.

**Cause:** Unchecked request value types reach scalar operations/database binding in [login.php](../login.php) and [dashboard.php](../client/dashboard.php).

### F05 - P2: Invalid stock quantities are silently changed

**Reproduce:** POST a test inventory resource with `quantity=-5`.

**Observed:** The resource is saved with quantity zero and Missing status. The resulting stock state is internally consistent, but it does not explain that the entered quantity was invalid.

**Cause:** Integer conversion and clamping in [inventory_action.php](../director/inventory_action.php). Reject invalid/out-of-range values before saving.

### F06 - P2: Some director updates do not validate CSRF tokens

**Reproduce:** Send an authenticated POST to `/director/account.php` with `update_account=1`, a test full name and phone, without a token.

**Observed:** The test account was updated successfully. Source inspection found the same missing token-validation pattern in package, inventory and parlor saves and admin shop saves. Those additional cases are source findings, not all independent live exploit demonstrations.

**Expected:** Consistent token enforcement on state-changing forms, matching the protected inquiry/feedback handlers.

The Strict SameSite session cookie reduces ordinary cross-site attack exposure. The audit established missing server validation, not an unauthenticated account takeover.

### F07 - P2: Overlength profile names are silently truncated

**Reproduce:** Submit a 280-character full name on the test director's account page.

**Observed:** HTTP 200/success and a stored name of 200 characters. No field-specific length message appeared.

**Expected:** Enforce the database limit before saving and explain the limit rather than discarding part of the name.

### F08 - P2: The sample-license directory bypasses private-document filename rules

**Reproduce:** Request `/uploads/sample-licenses/UC_Ddash.jpg` anonymously.

**Observed:** HTTP 200. The current files are user-supplied diagram samples. Standard test valid-ID files correctly returned HTTP 403.

**Cause:** [Upload rules](../uploads/.htaccess) protect filename prefixes such as `valid_id_` and `parlor_license_`; these sample filenames do not match. Real documents placed in this folder would inherit its public accessibility.

## 3. Design & UI Inconsistencies

| ID / priority | Reproduced observation | User impact |
|---|---|---|
| U01 / P2 | Registration at 320px has a 365px document width. Password/show-button groups extend outside their card. | Narrow-phone users must scroll sideways to reach controls. |
| U02 / P2 | A permitted 200-character package title breaks client search, the client catalog and the director package catalog. At 320px, measured widths reached 3,089px for search and 3,436px for catalogs. The issue also occurs at desktop widths. | One long published title can disrupt package comparison for clients. |
| U03 / P2 | At 320px, director dashboard, parlor list and inventory measured 398px, 427px and 488px respectively with the synthetic names used. | Status pills/cards and actions exceed the viewport. |
| U04 / P2 | At 1024px, 50 visible form controls across nine sampled pages lacked an associated HTML label or ARIA name. The questionnaire controls were correctly associated. | Screen-reader naming and label-click behavior are inconsistent. |
| U05 / P3, source inspection | Admin shop editing uses a plain narrow form and indigo Save button, while most management forms use styled cards and funeral-brand colors. | The secondary admin tool feels like a different interface. Live admin shop rendering was not tested. |

The long-title and narrow-width failures reproduced after waiting for page animations to finish. Screenshots include [registration at 320px](../.codex-review/20261020-qa-audit/browser-recheck/registration-320.png), [client search at 320px](../.codex-review/20261020-qa-audit/browser-recheck/client_dashboard-320.png), [director dashboard at 320px](../.codex-review/20261020-qa-audit/browser-recheck/director_dashboard-320.png) and [inventory at 320px](../.codex-review/20261020-qa-audit/browser-recheck/inventory-320.png).

Use the [W3C reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) as the target for narrow layouts. Associate visible labels programmatically with controls; the distinction between visible labels and correct association is explained in [W3C label guidance](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html). These findings are limited checks, not a full WCAG assessment.

## 4. Redundancies & UX Friction Points

| ID / priority | Observation | Recommended direction |
|---|---|---|
| X01 / P2 | Registration shows validation errors but clears entered name/email/phone. Password mismatch plus malformed email reproduced this. | Preserve safe text fields and highlight the affected inputs; passwords and files require appropriate handling. |
| X02 / P3 | Successful login redirects to the general homepage, then asks the user to select Go to Dashboard. | Redirect to the role dashboard, or explain why the homepage is the intended destination. |
| X03 / P2 gap | Clients have no visible account/profile/change-password destination. `/client` contains no corresponding account page. | Provide basic profile/password management if supported by the product requirements. This is a capability gap rather than a failed inquiry action. |
| X04 / P3 | Account approval and parlor approval are separate gates; users depend on an administrator but have limited status guidance. | Keep the required checks and show a short progress/status explanation. Do not silently remove business approval rules. |
| X05 / P2 maintenance risk | Inventory request handling runs repeated `ALTER TABLE` operations. | Move schema work into versioned migrations. Locking/production-load impact was not stress-tested; local request timings alone do not resolve that risk. |
| X06 / P3 | README calls the client dashboard booking UI, and the workflow document still mentions detailed read-only reviews on Package Details even though that section was intentionally removed. | Align documentation with the current inquiry/confirmation flow and current page layout. |

Empty states for no inquiries, pending confirmation and unavailable feedback were understandable. The 22-question scale and selected states were consistent. No additional detailed reviews widget or director-side repeat-service step should be reintroduced merely to address the issues above.

## 5. Actionable Recommendations

| Order | Changes | Acceptance checks |
|---|---|---|
| 1 | **F01:** Archive packages instead of hard-deleting used packages. Plan retention behavior for parlor/account removal and preserve necessary snapshots/references. | Deleting/hiding a published package does not erase an existing client's inquiry, questionnaire answers or rating history. Test this on synthetic data before any migration. |
| 2 | **F02, F08:** Move repository/research/setup files outside the public document root or deny them at the server. Protect the entire sample-license folder and keep authenticated document serving. | Anonymous repository-object, workbook, SQL and private-document URLs return 403/404; legitimate public package images and admin document viewing still work. |
| 3 | **F03-F05, F07:** Validate scalar types, finite numeric values, non-negative bounded quantities and field lengths before writes. Use field-level validation. Label intentionally zero/custom prices clearly. | Invalid price/quantity/array/overlength requests produce controlled errors and no altered or partially inserted rows. Valid values are preserved exactly. |
| 4 | **F06:** Apply the shared CSRF check and hidden token consistently to mutation forms. | Missing/invalid token returns 403; valid saves continue to work. Retain current role and ownership checks. |
| 5 | **U01-U03:** Bound grid/flex children with `min-width:0`, use single-column mobile grids, permit long names/titles to wrap with `overflow-wrap:anywhere`, and wrap/stack status/actions. | Re-run ordinary and 200-character-title cases at 320, 375, 768, 1024 and 1536px. Document width stays within the CSS viewport without hiding essential actions. |
| 6 | **U04, X01:** Give controls stable IDs and corresponding labels, retain safe values after errors and associate error text with its control. | Every visible form control has an accessible name; keyboard selection works; validation does not force users to re-enter unrelated details. |
| 7 | **U05, X02-X06:** Standardize secondary forms, simplify post-login navigation, agree client account-management scope, align documentation and remove request-time schema operations through reviewed migrations. | Existing inquiry confirmation, repeat inquiries, one questionnaire per confirmed experience, rating averages and admin catalog alignment remain unchanged. |

Before release sign-off, rerun the live dedicated-account cycle and the existing regression suite after fixes, then add authenticated live admin coverage, physical-device/browser coverage and deployed Firebase/configuration verification. Preserve the existing review data throughout that work.
